## 1. "Most recent email"

### R1 — Mailbox identity

The mailbox is the operator-selected, currently visible Gmail Inbox view. If Gmail publishes inbox categories, the selected visible category is part of the mailbox identity; the system never silently unions categories or searches another mailbox. If more than one Gmail window or tab is visible, or if categories are published and none is discernibly selected, the mailbox is ambiguous and the correct result is refusal (R7c) — the system never picks one for the operator.

### R2 — Admissible ordering evidence (closed allowlist)

"Most recent" means newest according to Gmail's own published ordering evidence for that visible mailbox. **The allowlist is closed: evidence that is not R2a or R2b is inadmissible, whether or not R3 names it.** Exactly two classes are admissible.

- **R2a — Published absolute datetime values.** Each candidate row publishes a **machine-readable absolute datetime** (a datetime-valued accessibility property resolving to an instant without inference), and the selected row's value compares strictly newer than every other enumerated candidate. **Human-facing time labels are not R2a evidence** — `2:14 PM`, `Aug 3`, `3/14/24`, and `Yesterday` are not standalone-resolvable, and comparing across those granularities is inadmissible. Wall-clock or locale inference to repair such a label is forbidden. **R2a additionally requires complete enumeration**: if the traversal budget ends before every candidate row in the visible mailbox has been enumerated, R2a is unsatisfied (→ R7e). A bounded window is not a mailbox.
- **R2b — A declared sort order.** The list container publishes an explicit sort/order property naming the sort key as received time **and its direction**, and the selected row is the extremum **in the newest direction** under that declared order — which is the last row under a declared ascending sort, not positionally first. R2b does not require complete enumeration, because the container asserts the order.

### R3 — Named inadmissible evidence

Illustrative, not exhaustive — R2 is the closed list. None of the following is recency proof, alone or in combination: DOM/tree traversal order; a row index; `posinset`/`setsize` without a declared sort order per R2b; visual y-position or geometry; "the first row the traversal returned"; a bold/unread style; a sort control's label or tab text such as a button reading "Newest" (a control is not a container order property); a thread-level last-activity time used as a message received time; a relative-age label such as "2 days ago"; or any inference from mutable markup. "Alone or in combination" means what it says: combining two inadmissible signals does not produce admissible evidence, and adding an inadmissible signal to admissible R2a or R2b evidence neither strengthens nor weakens it.

**R2b does not depend on anything named here.** R2b rests entirely on the container's own published sort property — the declared sort key and direction — and the row's position under that declared order is read from the container's assertion, not from traversal order, a row index, `posinset`, or geometry. Those signals supply no independent evidence and are never a substitute for the declared property: without it, R2b is unsatisfied no matter what position evidence is present. Where evidence is inadmissible, absent, or ambiguous, the correct result is refusal, not a best guess.

### R4 — Selection stability

The chosen candidate must still attest as the same message when its answer fields are read. A stale, reordered, duplicated, or ambiguous candidate fails closed; no second-best guess is spoken.

### R5 — Minimum spoken result

Sender, subject, and Gmail-published received time. Sender precedence is display name when Gmail publishes one, otherwise the address; publishing neither is a field-association failure, not an empty value. Subject is spoken as "no subject" **only** when Gmail explicitly publishes an empty subject; an absent or unreadable subject is a field-association failure. Message body and snippet are outside this north-star request unless a later explicit user turn asks for them.

### R6 — Answer audit

The audited artifact is **the daemon's audit record** — the same record [00-PRODUCT.md](00-PRODUCT.md) requires to name what was answered and why. The matrix column `answer audit` states that record's cardinality. The audit is a **set of element identities, deduplicated**: an identity that qualifies under both clauses below is counted once. Membership is conditioned on answering, and covers exactly:

- **R6a** — the element identities whose values were spoken (the R5 fields), and
- **R6b** — the element identities whose values established the selected message's recency under R2: under R2a, the selected row's own absolute-datetime element; under R2b, the container element carrying the declared sort order. R6b deliberately reaches outside the row for R2b, because that is where R2b's evidence lives.

Consequently the success cardinalities are fixed, not chosen: **under R2a, exactly 3** — sender, subject, and the datetime element, whose value is both the spoken received time and the recency evidence, counted once. **Under R2b, exactly 4** — those three plus the container's sort-order element.

- **R6c** — Candidate rows examined and rejected are **not** answered; their values never enter the audit, even when their timestamps were compared. Comparison is how R2a is evaluated; it is not answering.
- **R6d** — Any outcome that speaks no answer has audit cardinality **exactly 0** — including a refusal after ordering evidence was read — **except the R6e case**.
- **R6e** — The sole nonzero-audit failure class: a failure occurring after one or more R5 answer fields were already read records exactly those answer elements, and speaks no invented result. Ordering evidence read before any answer field does not make an outcome R6e; a refusal at the ordering stage is R6d.
- **R6f** — Every matrix row states a concrete integer and the named identity roles, never an unbound "N", and never a count inferred after the run.

## 2. Honest refusal classes and their discriminators

Product prose may be conversational, but it must preserve the measured cause without claiming absence. Each class names the measured signal that selects it, and the classes are a **decision table evaluated top to bottom** — the first row whose signal holds wins, so no two classes can claim the same evidence. The ordering is load-bearing: **R7f is evaluated first**, because a refusal the daemon returned is always reported as the daemon's refusal, never re-derived hub-side into a prettier cause.

| order | class | selecting signal (first match wins) | spoken shape |
| --- | --- | --- | --- |
| 1 | **R7f — Daemon refusal** | The daemon returned a refusal class for this request — a *policy* decision by the daemon, including a denied Gmail identity or a declined read. | Preserve the daemon's class and remedy. The hub may sanitize unsafe provider prose but may not rewrite the measured cause. |
| 2 | **R7a — Not permitted** | The **hub-side** permission check refuses before any request reaches the daemon. No daemon refusal exists. | Access is not allowed; permission is the remedy. |
| 3 | **R7b — Not running or unreachable** | A **mechanical** outcome, not a policy one: no Gmail application or window appears in the inventory, or the route to it errors at the transport level. | Gmail cannot be reached or read now. Do **not** say uninstalled unless inventory proved it. |
| 4 | **R7c — Signed out, no Inbox, or ambiguous mailbox** | A Gmail window is readable, but no Inbox view is published, a sign-in surface is published instead, or R1's mailbox identity is ambiguous. | Ask the operator to sign in, or to open/select one Inbox. Do **not** describe an empty inbox. |
| 5 | **R7d — Empty selected mailbox** | Gmail publishes an **explicit empty-state element** for the selected view. | The selected visible mailbox has no messages. |
| 6 | **R7e — Cannot determine newest** | An Inbox view is readable and **no explicit empty-state element is published**, but: R2 evidence is absent, inadmissible, or ambiguous; R2a evidence fails to single out exactly one candidate (a tie on published datetime); the traversal budget ended before complete enumeration; zero candidate rows were found without an empty-state element; R4 attestation failed; or R5 fields could not be associated. | The newest message cannot be determined reliably from the visible Gmail surface. |
| 7 | **R7g — Provider or session failure** | The provider socket or voice session failed. | The voice session failed. Close once, leave phrase wake armed, imply no desktop success. |

R7e is deliberately the wide net beneath a readable, non-empty-state inbox: anything that leaves the newest message undetermined lands here rather than being narrated as absence.

## 3. Dismissal and correlation

- **R8** — "Never mind," "stop," and a declined follow-up close the microphone, provider, and global voice session immediately and exactly once; phrase wake remains armed.
- **R9** — Dismissal permanently revokes this request's authority to publish into that conversation. **The observable contract is frozen: no result from a dismissed request is ever spoken.** Whether the in-flight desktop read is cancelled at its next checkpoint or allowed to run to completion unheard is an unobservable implementation choice belonging to a later stage; it is a declared non-decision, not a matrix ambiguity, because both branches produce the same observable row. Dismissal cannot keep the microphone open and cannot cancel unrelated background work.
- **R10** — Scope: R10 governs terminal closes that are **not** dismissals (inactivity close, provider failure). For those, a late result is never spoken into a different or newly awakened conversation; reuse requires a fresh correlated disclosure decision that tells the user the result belongs to the earlier request. **After a dismissal, R9 is absolute and R10 offers no reuse path** — a dismissed request's result is never spoken, in any conversation, under any correlation.
- **R11** — Re-wake always creates a new provider conversation; it does not revive the dismissed session or inherit its admission.
- **R12** — Dismissal arriving during model speech is a dismissal like any other: speech stops, voice closes once, no answer is completed.

## 5. What this document does not decide

Silence is not permission. These are deliberately open, and a later stage must decide them explicitly rather than infer them:

- Whether in-flight desktop work is cancelled or allowed to finish unheard after dismissal (R9). The observable contract is frozen either way.
- The exact Gmail application identity and permission grant shape.
- Which accessibility attributes carry R2a datetime values and R2b declared sort order on the real surface. The admissible *classes* are frozen here; no third class may be added by measurement.
- Traversal budget numbers. Exhaustion behavior is already frozen as R7e, and R2a's complete-enumeration requirement means a budget smaller than the mailbox makes R2a success unreachable rather than approximate.

**Time-label repair is not open.** R2a's rejection of human-facing labels and cross-granularity comparison is frozen. If the live Gmail surface publishes no absolute datetime, the honest consequence is that success is reachable only via R2b and every other case is R7e — a finding to report and rule on as an amendment, not a licence to widen R2a.

This document specifies no transport, no correlation message schema, no Gmail selector or query algorithm, and no checkpoint storage.
